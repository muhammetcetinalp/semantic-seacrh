Bir full-stack komuta kontrol uygulamasına entegre edilecek bağımsız bir Search Service geliştireceğiz.

Bu servis büyük miktarda structured ve unstructured verinin aranmasını sağlayacak. Amaç yalnızca klasik keyword search değil, semantic search ve structured filtering yeteneklerini de tek servis altında birleştirmek.

Aşağıdaki mimari ve teknik kararlar kesinleşmiştir. Bunları temel alarak projeyi tasarla ve implemente et.

## Temel Amaç

Search Service, mevcut ana uygulamadan bağımsız bir servis olacak.

Ana uygulama OpenSearch'e doğrudan erişmeyecek.

Tüm arama ve indexing işlemleri bu servis üzerinden yapılacak.

Genel yapı:

```text
Application
    |
    v
Search Service
    |
    +-- Search API
    |
    +-- Indexing / Synchronization
    |
    +-- Embedding Component
    |
    v
OpenSearch
    |
    +-- BM25
    +-- Vector Search
    +-- Structured Filters
    +-- Hybrid Search
```

İlk aşamada AI / Agent entegrasyonu yapılmayacak.

Öncelikle bağımsız, temiz ve production-oriented bir Search Service oluşturulacak.

# Temel Mimari Kararlar

## 1. OpenSearch Source of Truth Değildir

OpenSearch ana veri kaynağı olmayacak.

Asıl domain verileri mevcut sistemlerde / database'lerde bulunmaya devam edecek.

OpenSearch yalnızca:

* search
* indexing
* retrieval
* relevance ranking

için optimize edilmiş bir read/search model olacak.

---

## 2. Search Service OpenSearch'ü İzole Etmeli

Ana uygulama OpenSearch client veya query DSL bilmemeli.

Yanlış:

```text
Main Application
      |
      v
OpenSearch
```

Doğru:

```text
Main Application
      |
      v
Search Service
      |
      v
OpenSearch
```

OpenSearch'e erişim Search Service içerisinde bir adapter/client katmanının arkasında tutulmalı.

OpenSearch implementasyon detayları domain/service katmanlarına yayılmamalı.

---

## 3. Search Yaklaşımı

İlk versiyonda aşağıdaki arama yöntemleri desteklenecek:

### BM25 / Lexical Search

Exact kelimeler, isimler, kodlar ve text search için.

### Vector / Semantic Search

Anlamsal benzerlik için.

### Structured Filters

Örneğin:

```text
type
status
region
category
source
timestamp
priority
```

gibi alanlarda exact/range filtering yapılacak.

### Hybrid Search

BM25 ve vector search birlikte kullanılacak.

İlk tercih edilen ranking fusion yöntemi:

```text
RRF - Reciprocal Rank Fusion
```

olacak.

Temel yapı:

```text
Query
 |
 +--> BM25
 |
 +--> Vector Search
 |
 +--> Structured Filters
 |
 v
RRF
 |
 v
Ranked Results
```

---

# 4. Embedding Mimarisi

Embedding üretimi OpenSearch içerisine gömülmeyecek.

OpenSearch'ün temel sorumluluğu:

```text
vector saklamak
+
vector aramak
```

olacak.

Embedding üretimi Search Service tarafından yönetilecek.

Beklenen yapı:

```text
Search Service
      |
      v
Embedding Component / Service
      |
      v
Vector
      |
      v
OpenSearch
```

Örneğin:

```text
"Long range radar surveillance unit"
        |
        v
Embedding Model
        |
        v
[0.21, -0.74, 0.11, ...]
        |
        v
OpenSearch
```

Bu yaklaşım sayesinde embedding modeli OpenSearch'ten bağımsız değiştirilebilmeli.

İleride embedding modeli:

* local model
* remote model
* GPU server
* farklı embedding provider

olabilir.

Bu nedenle embedding erişimi interface/adapter arkasında tutulmalı.

Örneğin kavramsal olarak:

```java
EmbeddingProvider
```

gibi bir abstraction kullanılabilir.

Ancak gereksiz abstraction üretme.

---

# 5. Search Document Modeli

Mevcut structured ve unstructured veriler doğrudan rastgele şekilde OpenSearch'e yazılmayacak.

Domain verileri önce Search Service içerisindeki ortak search modeline dönüştürülecek.

Örneğin ileride şu tarz bir yapı olabilir:

```text
id
type
title
searchText
tags
metadata
createdAt
updatedAt
embedding
```

Ancak şu anda kesin SearchDocument field listesini belirleme.

Gerçek domain dataları görüldüğünde nihai modele karar verilecek.

Önemli prensip:

```text
Domain Object
      |
      v
DomainSearchMapper
      |
      v
SearchDocument
      |
      v
OpenSearch
```

Örneğin:

```text
Unit
 |
 v
UnitSearchMapper
 |
 v
SearchDocument
```

Yeni domain veri tipi geldiğinde mümkün olduğunca yalnızca yeni mapper eklenmesi yeterli olmalı.

# 6. Structured Field ve Semantic Field Ayrımı

Her field embedding'e dahil edilmemeli.

Örneğin:

```text
status
region
type
category
timestamp
priority
source
```

gibi alanlar structured filter olarak tutulmalı.

Örneğin:

```text
region = ANKARA
status = ACTIVE
timestamp > X
```

şeklinde sorgulanabilmeli.

Buna karşılık:

```text
description
name
report text
notes
human readable content
```

gibi alanlar:

```text
BM25
+
embedding
```

için kullanılabilir.

Hangi field'ların semantic content olacağı gerçek datalar görüldüğünde belirlenecek.

# 7. JSON'u Körlemesine Embed Etme

Şu yaklaşımı kullanma:

```text

```

Örneğin ileride:

```text
name

```

birleştirilerek:

```text

```

üretilebilir.

Sonra:


yapılabilir.

# 9. Dynamic Mapping Kullanımına Dikkat

Kontrolsüz dynamic mapping kullanma.

Çok sayıda farklı structured data tipi olduğu için field explosion / mapping explosion oluşabilir.

Önemli ve sorgulanacak alanlar açık mapping ile tanımlanmalı.

Çok değişken veya search açısından kritik olmayan alanlar kontrollü şekilde ele alınmalı.

---

# 10. Veri Senkronizasyonu

Search Service veri değişikliklerini OpenSearch ile senkronize edebilmeli.

Minimum olarak:

```text
CREATE
UPDATE
DELETE
```

işlemleri desteklenecek.

Mantıksal akış:

```text
Domain data changes
       |
       v
Search indexing layer
       |
       +--> CREATE -> index
       |
       +--> UPDATE -> update/upsert
       |
       +--> DELETE -> delete
       |
       v
OpenSearch
```

İlk tasarımda synchronization mekanizmasını clean şekilde ayrıştır.

İleride event-driven modele geçilebilmesi mümkün olmalı:

```text
DOMAIN_CREATED
DOMAIN_UPDATED
DOMAIN_DELETED
```

gibi eventler kullanılabilir.

Ancak ilk implementasyonu gereksiz yere Kafka vb. bağımlılıklarla karmaşıklaştırma.

---

# 11. Embedding Yeniden Hesaplama Politikası

Her update işleminde embedding yeniden oluşturulmayacak.

Örneğin:

```text
status:
ACTIVE -> INACTIVE
```

değişmişse ve status embedding içeriğine dahil değilse embedding yeniden hesaplanmamalı.

Ancak:

```text
description
```

gibi semantic content değişirse embedding yeniden oluşturulmalı.

Bu ayrım mimaride desteklenmeli.

---

# 12. Çok Hızlı Değişen Veriler

Sistemde bazı veriler:

* statik
* nadiren değişen
* zaman zaman değişen
* çok hızlı değişen

olabilir.

Örneğin canlı:

```text
position
state
telemetry
```

gibi veriler çok sık değişebilir.

Bu tip verileri her değişimde:

```text

+
OpenSearch reindex
```

yapmak istemiyoruz.

Search açısından gerçekten gerekli olan alanları indexle.

Çok hızlı değişen live state için ayrı indexing/update politikası oluşturulabilecek şekilde tasarla.

# 13. PostgreSQL

Search Service'in kendi PostgreSQL database'i olacak.

PostgreSQL OpenSearch'ün alternatifi değildir.

OpenSearch:

```text
search / retrieval
```

için kullanılacak.

PostgreSQL ise Search Service'in kendi persistent state ihtiyaçları için kullanılacak.

Örneğin ileride:

* indexing state
* synchronization state
* source metadata
* configuration
* failed indexing operations
* job information

gibi Search Service'e ait bilgileri tutabilir.

Ancak gereksiz tablolar oluşturma.

Önce gerçekten gerekli persistence ihtiyaçlarını belirle.

Spring Data'nın uygun çözümünü kullan.
