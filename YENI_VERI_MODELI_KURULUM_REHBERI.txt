1. ADIM: İndeks İstek Modelinin (IndexDocumentRequest.java) Kurgulanması
--------------------------------------------------------------------------------
Dosya Yolu: 
src/main/java/com/example/semantic_search/dto/IndexDocumentRequest.java

BU ADIMIN AMACI:
Kafka'dan gelen 70'ten fazla iç içe alanı olan karmaşık JSON verisini, arama
motorumuzun (OpenSearch) ve yapay zeka modelimizin (BGE-M3) anlayacağı standart,
temiz ve güçlü bir Java nesnesine (DTO) dönüştürmektir.

--------------------------------------------------------------------------------
A) OLMAZSA OLMAZ 3 ALAN VE TEKNİK GEREKÇELERİ:
--------------------------------------------------------------------------------
1. "id" (String) - Dokümanın Benzersiz Kimliği (Primary Key):
   - Neden Şart?:
     a) Güncelleme (UPSERT): Aynı ID ile yeni bir kayıt geldiğinde OpenSearch
        eski kaydı bulup günceller, mükerrer kayıt oluşmasını engeller.
     b) Silme (DELETE): Kafka'dan silme emri geldiğinde silinecek doküman bu
        ID ile bulunur.
     c) Tekilleştirme & Güvenlik (Idempotency): Ağ gecikmesiyle eski versiyonlu
        bir paket geç gelirse, sistem "Ben bu ID'nin yeni sürümünü zaten işledim"
        diyerek veri kirliliğini önler.

2. "indexName" (String) - Hedef OpenSearch İndeksi:
   - Neden Şart?:
     - Farklı topic'lerden gelen verileri farklı indekslere (örn: radar_indeksi,
       ihbar_indeksi, lojistik_indeksi) yazabilmemizi sağlar.
     - İleride silme, arşivleme ve veri ömrü (TTL) yönetimini kolaylaştırır.
     - NOT: Ayrı ayrı indekslere yazılsa dahi, arama yapılırken "POST /*/_search"
       veya "POST /radar,ihbar/_search" denilerek TEK BİR SORGUDAN hepsi taranabilir.

3. "searchText" (String) - Yapay Zeka (Embedding) Metni:
   - Neden Şart?:
     - BGE-M3 gibi yapay zeka modelleri 70 tane dağınık JSON alanını, iç içe sayıları
       ve teknik kodları tek tek anlayamaz; anlamlı bir Türkçe metin bekler.
     - Kullanıcının arama çubuğuna yazdığı sorgularla eşleşecek metinlerin
       (başlık, açıklama, detaylar) temiz bir şekilde birleştirilmiş halidir.
     - 1024 boyutlu vektör bu alandaki metinden üretilir.

--------------------------------------------------------------------------------
B) BM25 (KELİME ARAMASI) İÇİN KULLANILACAK ALANLAR:
--------------------------------------------------------------------------------
- Kullanıcının birebir kelime eşleşmesiyle aramasını istediğin ve aramalarda daha
  fazla puan (boost/ağırlık) almasını istediğin alanlar burada tanımlanır.
- Örnek:
  - "title" (Başlık - BM25'te 3 kat ağırlık verilebilir)
  - "raporDetayi" (Detaylı metin - BM25'te 2 kat ağırlık verilebilir)
  - "birim / kategori" (Özel sınıflandırma alanı)

--------------------------------------------------------------------------------
C) GERİYE KALAN 70+ İÇ İÇE ALAN İÇİN ESNEK TORBA (structuredFields):
--------------------------------------------------------------------------------
- 70 tane alan için tek tek Java değişkeni ve getter/setter YAZILMAZ!
- Bunun yerine şu alan tutulur:
  private Map<String, Object> structuredFields;

1. OPENSEARCH BU İÇ İÇE VERİYİ ALIP ARKA PLANDA NE YAPACAK?
   OpenSearch doğuştan NoSQL bir JSON motorudur. İç içe 5 kat derinlikte dahi
   obje olsa, otomatik olarak hepsini "Noktalı Yol" (Dot Notation) ile indeksler.
   
   Örnek Gelen JSON:
   {
     "structuredFields": {
       "radar": {
         "cihaz": {
           "irtifa": 12500,
           "kod": "RAD-99"
         }
       },
       "harekat": {
         "bolge": "Karadeniz"
       }
     }
   }

   OpenSearch bu veriyi aldığında arka planda şu yolları otomatik açar:
   -> "structuredFields.radar.cihaz.irtifa"  (Sayısal / integer olarak indeksler)
   -> "structuredFields.radar.cihaz.kod"     (Keyword / tam metin olarak indeksler)
   -> "structuredFields.harekat.bolge"       (Keyword / tam metin olarak indeksler)

2. BEN BU VERİLERLE NASIL FİLTRELEME YAPACAĞIM?
   Arama sorgusu atarken (OpenSearch Query DSL), hiçbir karmaşık SQL yazmadan
   doğrudan bu noktalı yolları vererek 3 temel filtre uygularsın:

   a) Sayısal Aralık Filtresi (İrtifası 10.000'den büyük olanlar):
      {
        "range": {
          "structuredFields.radar.cihaz.irtifa": { "gte": 10000 }
        }
      }

   b) Birebir Değer Eşleşmesi (Bölgesi "Karadeniz" olanlar):
      {
        "term": {
          "structuredFields.harekat.bolge.keyword": "Karadeniz"
        }
      }

   c) Hibrit Arama + Çoklu Filtre (Hem "arıza" ara, hem irtifa > 10.000 olsun):
      {
        "query": {
          "bool": {
            "must": [
              { "match": { "searchText": "arıza sinyal kaybı" } } // Yapay zeka & BM25
            ],
            "filter": [
              { "range": { "structuredFields.radar.cihaz.irtifa": { "gte": 10000 } } },
              { "term": { "structuredFields.harekat.bolge.keyword": "Karadeniz" } }
            ]
          }
        }
      }

3. JAVA KODUNDA BUNU NASIL KULLANACAKSIN?
   Java OpenSearch Client ile filtre eklemek 1 satırdır:
   .filter(f -> f.range(r -> r.field("structuredFields.radar.cihaz.irtifa").gte(JsonData.of(10000))))

5. OPENSEARCH BU ALANLARI FİZİKSEL OLARAK NEREDE VE NASIL SAKLAR?
   OpenSearch tek bir depolama yöntemi kullanmaz; her veri tipine göre en hızlı
   mekanizmayı seçer:
   
   a) Sayılar ve Tarihler (irtifa, hiz, tarih):
      -> "Doc Values & BKD Sayı Ağacı"nda saklanır (Sütun bazlı Excel sütunu gibi).
      -> Görevi: "irtifa > 10000" gibi sayısal aralıkları ve sıralamayı (SORT)
         mikrosaniyede çalıştırmaktır.
   
   b) Enum'lar, Kodlar ve Kategoriler (durum="ARIZALI", bolge="Karadeniz"):
      -> "Keyword Ters İndeksi"nde saklanır (Analizörsüz, harfi harfine tam eşleşme).
      -> Görevi: Dropdown ve filtre seçimlerini ışık hızında bulmaktır.
   
   c) Arama Metinleri (title, searchText):
      -> "Ters İndeks"te (Turkish Analyzer ile köklerine ayrılmış fihristte) saklanır.
      -> Görevi: BM25 kelime araması yapmaktır.
   
   d) Anlamsal Vektör (1024 boyutlu sayı dizisi):
      -> "HNSW Vektör Grafı"nda (Örümcek Ağı / FAISS) saklanır.
      -> Görevi: Anlamsal benzerlik ve yapay zeka aramasını çalıştırmaktır.
   
   e) 70 Alanın Orijinal JSON Hali:
      -> "_source" (Sıkıştırılmış Doküman Deposu) alanında saklanır.
      -> Görevi: Arama sonucunda tüm detayları ekranda göstermek için sana geri vermektir.

6. BU KADAR FARKLI ALANIN HANGİ VERİYE AİT OLDUĞUNU SİSTEM NEREDEN BİLİYOR?
   (İÇSEL DocID ZIMBALAMA SİSTEMİ)
   - Sen her alana ayrı ayrı ID VERMEZSİN! Sen sadece tek bir "id" verirsin (örn: "OLAY-1001").
   - OpenSearch bu dokümanı diske alırken ona tek bir içsel numara atar:
     Örnek: "DocID = 42"
   - Ve tüm parçaları bu 42 numarasına sımsıkı ZIMBALAR:
     * Ters İndekste "radar" kelimesi      -> [DocID: 42]'yi gösterir.
     * HNSW Vektör Ağındaki nokta         -> [DocID: 42]'yi gösterir.
     * İrtifa sütunundaki 12500 sayısı     -> [DocID: 42]'ye aittir.
     * _source içindeki 70 alanlık JSON    -> [DocID: 42]'nin dosyasıdır.
   
   SONUÇ:
   Kullanıcı ister irtifadan arasın, ister kelimeden, ister vektörden...
   OpenSearch anında "Bu 42 numaralı dokümandır" der ve _source deposundan
   o dokümanın orijinal tüm 70 alanını tek parça halinde önüne koyar!

2. ADIM: OpenSearch Varlık Modelinin (SearchDocument.java) Senkronize Edilmesi

BU ADIMIN AMACI VE BU SINIFIN GÖREVİ:
IndexDocumentRequest sınıfı Kafka'dan gelen "Ham İstek Formudur (DTO)".
SearchDocument ise OpenSearch diskinin içine fiziksel olarak kaydedilen
"Gerçek Veritabanı Varlığıdır (Entity)".

NEDEN İKİ AYRI SINIF VAR? BU CLASS NE İŞE YARAR?:
1. Yapay Zeka Vektörünü Taşımak İçin:
   - Kafka bize 1024 boyutlu yapay zeka vektörünü göndermez (Kafka sadece metin gönderir).
   - Servisimiz metni BGE-M3 modeline verir ve 1024 boyutlu vektörü alır.
   - İşte bu üretilen vektörü (float[] embedding) ve sistem zaman damgalarını
     (createdAt, updatedAt) dokümanın üzerine mühürleyip OpenSearch'e teslim
     eden sınıf SearchDocument'tir.
2. Arama Sonuçlarını Karşılamak İçin:
   - Kullanıcı arama yaptığında OpenSearch'ten dönen sonuçlar IndexDocumentRequest
     olarak dönmez; diske kaydedilmiş olan bu eksiksiz SearchDocument nesnesi olarak döner.

BU AŞAMADA NE YAPILMASI GEREKİR?:
- 1. Adımda IndexDocumentRequest içine eklediğin tüm yeni alanları (veya sildiğin alanları)
  birebir SearchDocument.java içine de yansıtırsın.
- Üzerine dokunmaman gereken 3 özel sistem alanı vardır:
  a) private float[] embedding; // 1024 boyutlu BGE-M3 yapay zeka vektörü
  b) private Instant createdAt; // Kayıt tarihi
  c) private Instant updatedAt; // Son güncelleme tarihi

1. "read(String message)" METODU (Paketi Açma ve Kimlik Tespiti):
   - Ne Yapar?: Kafka'dan gelen ham metni JSON nesnesine çevirir, formatını anlar ve doküman ID'sini bulur.

   A) ZARF (ENVELOPE) FORMATI NEDİR? (KARGO KUTUSU BENZETMESİ):
      İnternetten bir telefon kılıfı sipariş ettiğinde, ürün doğrudan çıplak kargolanmaz;
      bir kargo kutusunun (zarfın) içine konur.
      * Kutunun Dışında (Zarf Etiketi): Takip No ("eventId"), İşlem Tipi ("eventType": "SIL" veya "EKLE").
      * Kutunun İçinde ("data"): Asıl ürünün (telefon kılıfının) özellikleri durur.
      
      Zarflı Örnek JSON:
      {
        "eventId": "evt-1234",
        "eventType": "UPSERT",
        "version": 2,
        "data": {
          "id": 101,
          "baslik": "Radar Arızası",
          "irtifa": 12000
        }
      }

   B) DÜZ (ZARFSIZ) JSON FORMATI NEDİR?:
      Ürünün hiçbir koliye konmadan doğrudan gönderilmesidir:
      {
        "id": 101,
        "baslik": "Radar Arızası",
        "irtifa": 12000
      }

   C) GELEN VERİYE NASIL BAKMALI VE KODU NASIL GÜNCELLEMELİSİN?:
      Kafka'dan gelen örnek JSON mesajını önüne al ve şu soruya bak:
      "Benim asıl verilerim en dış katmanda mı duruyor, yoksa bir 'data' kutusunun içinde mi?"
      
      DURUM 1: Verin DÜZ JSON ise (En yaygın durum - Zarf yoksa):
      - Satır 56'daki zarf kontrolü otomatik olarak devre dışı kalır.
      - Kod doğrudan Satır 63-73 arasına geçer.
      
      BU BÖLÜMDE YAPILACAK BİREBİR KOD DEĞİŞİKLİĞİ (Satır 63-73):
      
      ESKİ (Yedeklerle dolu karmaşık hal):
      ------------------------------------
      String docId = root.path("id").asText(
              root.path("documentId").asText(
                      root.path("entityId").asText(java.util.UUID.randomUUID().toString())));
      String eventType = root.path("eventType").asText(
              root.path("type").asText(
                      root.path("action").asText("UPSERT")));
      String eventId = root.path("eventId").asText(java.util.UUID.randomUUID().toString());
      long version = root.path("version").asLong(1L);

      YENİ (Senin verine göre tertemiz ve sade hal):
      ----------------------------------------------
      String docId = root.path("id").asText(); // ID alanının adı 'id' ise bu yeterlidir!
      String eventType = "UPSERT";              // Düz veri her zaman ekleme/güncellemedir
      String eventId = java.util.UUID.randomUUID().toString();
      
      // DİKKAT! Sabit 1L yazarsan aynı ID için gelen 2. güncelleme STALE sayılıp silinir!
      // JSON'da 'version' alanı yoksa o anki zaman damgasını (milisaniyeyi) kullan:
      long version = root.path("version").asLong(System.currentTimeMillis());

      return new SearchIndexingEvent(eventId, eventType, docId, version, root);

      DURUM 2: Verin ZARF Formatında ise (Dışında eventType ve data varsa):
      - Kod Satır 56'daki "if (root.has("eventType") ...)" bloğuna girer.
      - Bu blok gelen paketi otomatik olarak SearchIndexingEvent nesnesine çevirir.
      - 'data' içindeki asıl dokümanın otomatik olarak mapDocument metoduna aktarılır.
      - Bu blok sayesinde koda dokunmana bile gerek kalmadan sistem zarfı tanır!

   C) YENİ VERİ MODELİNE GÖRE BİREBİR REFACTOR EDİLMİŞ ÖRNEK "mapDocument":
   -----------------------------------------------------------------------------
   @Override
   public IndexDocumentRequest mapDocument(SearchIndexingEvent event, KafkaIndexingProperties.EventRoute route) {
       if (event.data() == null || !event.data().isObject()) {
           throw new InvalidSearchEventException("Ekleme/Güncelleme olayları veri (data) alanında tam doküman gerektirir.");
       }
       try {
           IndexDocumentRequest request = objectMapper.treeToValue(event.data(), IndexDocumentRequest.class);
           if (request.getStructuredFields() != null
                   && request.getStructuredFields().keySet().stream().anyMatch(RESERVED_FIELDS::contains)) {
               throw new InvalidSearchEventException("Yapısal dinamik alanlar temel çekirdek alanların üzerine yazamaz.");
           }

           // 1. Kalan 70+ Alanı Dinamik Olarak Torbaya Doldur (Eski fieldsNode tamamen silindi!)
           if (request.getStructuredFields() == null) {
               request.setStructuredFields(new java.util.HashMap<>());
           }
           Map<String, Object> dataMap = objectMapper.convertValue(event.data(), Map.class);
           if (dataMap != null) {
               for (Map.Entry<String, Object> entry : dataMap.entrySet()) {
                   String key = entry.getKey();
                   if (!RESERVED_FIELDS.contains(key) && !"structuredFields".equals(key)) {
                       request.getStructuredFields().putIfAbsent(key, entry.getValue());
                   }
               }
           }

           // 2. Yapay Zekanın Okuyacağı Metni Seç ve Birleştir (searchText)
           if (request.getSearchText() == null || request.getSearchText().isBlank()) {
               StringBuilder sb = new StringBuilder();
               if (request.getTitle() != null && !request.getTitle().isBlank()) {
                   sb.append(request.getTitle()).append("\n");
               }
               if (request.getRaporDetayi() != null && !request.getRaporDetayi().isBlank()) {
                   sb.append(request.getRaporDetayi()).append("\n");
               }
               request.setSearchText(sb.toString().trim());
           }

           // 3. Kimlik ve Rota Mühürleri
           request.setId(event.documentId());
           request.setIndexName(route.indexName());
           request.setType(route.documentType());

           return request;
       } catch (JacksonException ex) {
           throw new InvalidSearchEventException("Doküman anlık görüntüsü geçerli değil.", ex);
       }
   }

1. TEMEL KURAL: KAFKA PARTITION VE THREAD (CONCURRENCY) ALTIN İLİŞKİSİ
   -----------------------------------------------------------------
   Kafka'da paralellik "Topic Partition" seviyesindedir. 
   
   FORMÜL:
     Toplam Tüketici Thread Sayısı = (Uygulama Pod / Sunucu Sayısı) x (concurrency)

   * ALTIN KURAL: Toplam Thread Sayısı, Topic'in Partition Sayısından FAZLA OLAMAZ!
     - Örnek: "radar-events" topic'inde 3 partition varsa:
       Sen concurrency = 6 yaparsan veya 2 pod x 3 concurrency = 6 thread açarsan,
       Sadece 3 thread çalışır, kalan 3 thread BOŞTA (idle) bekler, CPU/RAM israfıdır.
     - Eğer sistemde veri yükü arttıysa ve daha hızlı tüketim isteniyorsa:
       1) Önce Kafka tarafında Topic partition sayısı artırılır (örn: 3 -> 12).
       2) Ardından uygulamada concurrency veya pod sayısı artırılır (örn: 3 pod x 4 concurrency = 12 thread).

2. BROKER SAYISI DEĞİŞTİĞİNDE KOD GÜNCELLENİR Mİ?
   ------------------------------------------------
   -> KOD DEĞİŞİKLİĞİ GEREKMEZ!
   - Neden?: Spring Boot'un "spring.kafka.bootstrap-servers" özelliği harici ortam
     değişkeniyle yönetilir.

     "KAFKA_BOOTSTRAP_SERVERS" ortam değişkenine virgülle ayrılarak yeni broker IP'leri girilir.
   - Örnek: KAFKA_BOOTSTRAP_SERVERS="10.0.1.10:9092,10.0.1.11:9092,10.0.1.12:9092"

   refaktör yapılması gerekir:

   A) SENARYO 1: BATCH (TOPLU) TÜKETİM VE BULK INDEXING REFAKTÖRÜ (YÜKSEK TRAFİK)
      - Neden?: Şu anki kodumuzda (KafkaIndexingListener.java) her mesaj TEK TEK
        (record by record) işlenir. Saniyede 10.000+ mesaj aktığı durumlarda OpenSearch'e
        ve Embedding servisine tek tek istek atmak sistemi kilitler. Toplu paketleme gerekir.
      - Nerede Değişiklik Yapılır?:
        1) "KafkaIndexingConfiguration.java":
           factory.setBatchListener(true); // Container batch moduna alınır
           factory.getContainerProperties().setAckMode(ContainerProperties.AckMode.BATCH);
        2) "KafkaIndexingListener.java":
           // Metot parametresi tek record yerine List yapılır:
           @KafkaListener(...)
           public void listen(List<ConsumerRecord<String, String>> records) {
               // Toplu metin embedding'i ve OpenSearch Bulk API çağrısı
           }

   B) SENARYO 2: TOPIC BAŞINA FARKLI CONCURRENCY VE AYRI DİNLİYİCİ REFAKTÖRÜ
      - Neden?: Şu an tüm topic'ler tek bir @KafkaListener ve tek bir concurrency
        ile dinlenmektedir. Fakat diyelim ki "radar" topic'i 12 partition'a sahip ve
        çok yoğun; "ihbar" topic'i ise 1 partition'a sahip ve sakin. Tek bir factory
        kullanmak kaynakları verimsiz böler.
      - Nerede Değişiklik Yapılır?:
        1) "KafkaIndexingConfiguration.java":
           İki ayrı factory tanımlanır:
           - highThroughputContainerFactory (concurrency = 8)
           - standardContainerFactory (concurrency = 1)
        2) "KafkaIndexingListener.java":
           Tek metot yerine topic'lere göre ayrılmış iki listener metodu yazılır:
           @KafkaListener(topics = "radar-events", containerFactory = "highThroughputContainerFactory")
           public void listenRadar(ConsumerRecord<String, String> record) { ... }

           @KafkaListener(topics = "ihbar-events", containerFactory = "standardContainerFactory")
           public void listenIhbar(ConsumerRecord<String, String> record) { ... }

   C) SENARYO 3: MANUEL ACKNOWLEDGMENT (TAM GÜVENLİ TRANSACTION) REFAKTÖRÜ
      - Neden?: Şu anki mod "AckMode.RECORD"dur. Eğer işlem sırasında veri tabanına
        yazılamadan pod ölürse mesajın kaybolmaması veya garantiye alınması için
        manuel commit (Acknowledgment) gerekebilir.
      - Nerede Değişiklik Yapılır?:
        1) "KafkaIndexingConfiguration.java":
           factory.getContainerProperties().setAckMode(ContainerProperties.AckMode.MANUAL_IMMEDIATE);
        2) "KafkaIndexingListener.java":
           public void listen(ConsumerRecord<String, String> record, Acknowledgment ack) {
               try {
                   processor.process(record.value());
                   ack.acknowledge(); // Sadece işlem 100% başarılı olunca Kafka'ya onay ver
               } catch (Exception e) {
                   // Hata stratejisi
               }
           }
